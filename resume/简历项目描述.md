## 简历 bullet（精简版，直接可用）

**MedRAGent-Dify｜医学文献自动检索与筛选系统（个人项目，Python / Dify / DeepSeek）**

- 基于 Dify Cloud 编排 **15 节点 Workflow**（开始/结束 + 知识检索 + LLM×4 + HTTP×2 + 代码×5 + 迭代）重构医学文献自动筛选管线：PICOS 解析 → MeSH 主题词映射 → PubMed 布尔检索式生成 → 逐篇纳入/排除判定 → 筛查报告，接入 DeepSeek-V4.1-Flash（deepseek-flash），迭代节点 4 路并行，发布为 Service API（SSE 流式）
- **HTTP 请求节点直连 NCBI E-utilities 公网 API**（esearch JSON + MEDLINE 纯文本双端点，纯字符串解析规避沙箱包限制，重试容错零部署）；另实现 FastAPI 工程化封装（限速/重试/指数退避，可容器化部署并注册为 Dify 自定义工具）；将 MeSH 2026（3 万+ 医学主题词，按目标分支裁剪为 2,977 条）构建为 Dify 原生知识库，配置 **bge-large-en-v1.5 稠密嵌入 + 混合检索 + bge-reranker-v2-m3 重排**（bge-m3 多向量在 50MB 向量配额下超限，改用稠密模型 + 平台混合检索），替代原自研 FAISS 方案
- 在真实系统综述案例（Ramadan 禁食 × 青少年 1 型糖尿病）上端到端验证：原管线检索命中与原作者公开结果 **PMID 100% 重合**（44/44）；V3→V4.1-Flash 判定一致率 **89.2%**；Dify 版经 Service API 实跑（命中 3,293 / 筛选 44 / 纳入 10），与原基线重合的 7 篇文献判定 **7/7 一致**；产出 Dify/RAGFlow/MaxKB 三平台选型对比文档

## 面试问答准备

### 1. 为什么用 Dify？和 RAGFlow/MaxKB 比呢？（JD 直接相关，必考）

30 秒版见 [docs/platform-comparison.md](../docs/platform-comparison.md)。要点：三者定位不同——MaxKB 是开箱即用的知识库问答，RAGFlow 强在复杂文档解析（DeepDoc）与引用溯源，Dify 强在工作流编排 + 工具生态。我的场景核心是**多阶段编排 + 外部 API 工具集成**，知识库只是辅助角色，所以 Dify 最优；换成扫描件病历问答我会选 RAGFlow。能落地这个判断本身就是"熟练使用"的证明。

### 2. 工作流是怎么设计的？为什么这么拆节点？

- **职责单一**：每个 LLM 节点只做一件事（映射 / 组装 / 判定 / 报告），便于定位坏环节、单独调提示词；
- **知识检索节点前置**：PICOS 全文先在 MeSH 知识库里召回候选规范主题词（TopK=8），LLM① 只在召回结果里做映射——这是"检索增强"思想，保证 LLM 只用真实存在的规范词（原项目用 FAISS 相似度阈值 0.6 起同样的作用）；
- **迭代节点做逐篇筛选**：天然并发、每篇独立重试，替代原项目 Python for 循环；
- **Code 节点做数据清洗与兜底**：工具 JSON 解析、LLM 输出的 JSON 截断容错——**不要让 LLM 做确定性的活**。

### 3. 外部 API 怎么集成的？踩过什么坑？

- **主路径：HTTP 请求节点直连** NCBI E-utilities（它本身是公网 API，无需鉴权）：esearch 用 JSON 端点拿 PMID 列表，efetch 用 **MEDLINE 纯文本端点**（4 字符标签 + 缩进续行的稳定格式）拿文献详情——特意避开 XML，因为 Dify 代码沙箱对包有白名单限制，纯字符串状态机解析最稳；
- **工程化封装（加分项）**：`tool-service/` 用 FastAPI 把 esearch/efetch/MeSH 同义词扩展封装成 REST 端点（限速节流、指数退避重试、OpenAPI Schema 自动生成），可容器化部署到 Render/HF Space 后注册为 Dify 自定义工具；
- **坑①**：E-utilities 必须打到具体端点 `/esearch.fcgi`，打 base URL 是 404；
- **坑②**：Biopython 的 E-utilities 传输在某些网络路径下对长查询**间歇性 400**（复现后二分定位确认），换成 requests GET 直连修复——教训：依赖库的传输层不可控时，直接走稳定的标准 HTTP；
- **坑③**：NCBI 无 key 限 3 req/s → 节流 + 退避，配 Entrez key 提到 10 req/s。

### 4. 提示词工程上做了什么？（Prompt Engineering 必考）

- **规则前置、数据后置**：判定规则与输出格式放 system，文献内容放 user/变量占位，防止长文本淹没指令；
- **缺省决策规则**：移植原项目的"未找到明确支持/否定描述→视为满足/不满足"，消除 LLM 犹豫输出（这是文献筛选场景的关键方法学决策）；
- **结构化输出**：严格 JSON + 温度 0.1 + Code 节点括号截断兜底，不依赖 function calling；
- **元素级理由**：要求按 PICOS 每个元素给 match 理由 + 排除原因列表，可解释、可复核（report.xlsx 列结构对齐）。

### 5. 和原自研 Python 管线比，平台化重构得到/失去了什么？（体现工程判断力）

**得到**：可视化编排与调试、知识库/向量库托管、迭代并发、一键发布 API、非工程同学也能改提示词；**失去/注意**：灵活度受平台节点能力约束、调试黑盒化（靠节点级 elapsed/trace）、Sandbox 版有运行次数与迭代并发限制。**方法论**：先有自研管线（懂底层），再平台化（懂提效）——两层都碰过，选型才有依据。

### 6. 检索质量怎么保证？怎么评估？

- 知识库层面：混合检索（向量+全文）+ 重排，召回测试验证（如 `type 1 diabetes adolescent fasting` 命中 `Diabetes Mellitus, Type 1`）；
- 端到端层面：与原项目公开报告（同一 PICOS）做**一致性对比**：检索命中 PMID 100% 重合（44/44）；模型换代（V3→V4.1-Flash）判定一致率 89.2%，4 处差异全为边界案例且方向一致（Flash 更宽松）；Dify 版经 API 实跑后，与基线 PMID 重合 7 篇、判定 7/7 一致（两版检索式口径不同，Dify 更宽，所以不比较纳入总数，只比较交集）；
- 局限性要主动讲：LLM 筛选是辅助筛查，最终仍需人工复核（报告"方法学说明"一节写明了）。

### 7. 如果要优化，下一步做什么？（展示 roadmap 意识）

- 检索式组装节点后加**校验循环**（LLM 判定检索式语法 → 错误重生成，LLM-as-judge）；
- 同义词扩展也走工具调用（`/mesh/expand` 已就绪，可加分支节点）；
- 引入会话变量记忆，支持"追加排除标准后增量重筛"；
- DSL 版本升级 + 多租户参数模板化（不同综述模板）。

### 8. 可能的追问快答

- **为什么用 deepseek-flash？** 判定/抽取类任务 Flash 档够用，成本低、延迟小；需要复杂长链推理时再切 DeepSeek-R 系列（换模型只需在 Dify 节点里重选，管线不用动）。
- **为什么 GET 不是 POST？** Dify 自定义工具兼容性 + 参数自动编码；服务端语义也是只读检索。
- **知识库为什么不用父子分块？** MeSH 词条是短小独立的结构化条目，单条即最优块，父子分块反而稀释召回。
- **为什么 Dify 版两次运行纳入数不一样（15 / 10）？** LLM 在边界文献上的判定有非确定性（温度 0.1 也非零），并行不改变单篇输入但模型输出会波动；因此报告明确写“LLM 辅助初筛、需人工复核”，这也是文献筛选场景必须保留人工环节的原因。
- **为什么嵌入用 bge-large-en 而不是 bge-m3？** bge-m3 是多向量模型（dense+sparse+ColBERT），同一分段会写多份向量，Sandbox 50MB 配额下约 3,000 段就超限；换成纯稠密 1024 维的 bge-large-en，再用 Dify 的混合检索（向量 0.7 / 全文 0.3）补回关键词召回。
- **并发与稳定性？** 迭代节点并发受 Sandbox 限制；工具服务无状态可横向扩容；PubMed 有内置节流，不会打爆 NCBI。
- **数据安全？** 全链路只传文献元数据（题目/摘要），无患者数据；密钥全部走平台配置，不进仓库。
